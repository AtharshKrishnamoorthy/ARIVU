The Arivu framework manages multi-turn continuity via an isolated memory layer (`arivu.memory.store`). This abstraction prevents you from needing to pass raw chat arrays manually back and forth during pipeline invocation.

## Storage Backends

You can define the scope of your memory persistence using the `ARIVU_MEMORY_BACKEND` environment variable prior to engine instantiation.

<CardGroup cols={2}>

## The Memory Store Lifecycle

The `memory_write` node at the terminal end of the execution graph directly invokes the database proxy to commit the interaction payload. 

### Data Logged
1. **The Origin Prompt** (`question`)
2. **The Evaluated Syntax** (`sql`)
3. **The LLM Synthesis** (`response`)
4. **Execution Traces** (`trace_events`: containing latency, tokens consumed, and intermediate node data for Dashboard visualization)

### Admin Gate Tracking
When a destructive query is detected, the pipeline halts and calls `save_pending_approval()`. 
Any registered frontend integration can ping `get_pending_approval(session_id)` to retrieve the queued payload. Calling `resolve_approval(session_id, True)` unlocks the gate, allowing the graph to route to the execution node.
